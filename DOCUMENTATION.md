# Space Mini App - technical notes

Engineering notes on the app sections: UI, server APIs, the admin panel, cases,
missions, i18n and theming. For the short project overview and the setup guide
see [README.md](README.md).

## Мультиязычность (i18n)

В приложении три языка: русский (`ru`), украинский (`uk`) и английский (`en`).
Переключение доступно кнопкой с глобусом в шапке (шит с выбором) и в панели
«Язык» на экране профиля. Выбор пользователя сохраняется в `localStorage`.

### Структура

| Файл | Назначение |
| --- | --- |
| `src/i18n/locales/ru.js` | базовый словарь, источник истины по набору ключей |
| `src/i18n/locales/uk.js`, `src/i18n/locales/en.js` | переводы с той же структурой ключей |
| `src/i18n/locales/index.js` | реестр локалей: метаданные (название, короткий код, флаг, `Intl`-локаль) и алиасы для автоопределения |
| `src/i18n/index.js` | ядро без React: `t()`, `tp()` (числительные), `setLocale()`, автоопределение языка, `Intl`-форматирование |
| `src/i18n/I18nProvider.jsx`, `src/i18n/I18nContext.js` | React-провайдер и хук `useTranslation()` |
| `src/i18n/serverMessages.js` | перевод текстов бэкенда (ошибки API, названия и описания наград) |
| `src/components/layout/LanguageSwitcher.jsx` | переключатель языка |
| `src/utils/caseText.js` | хелперы текстов кейсов/наград по ключам словаря |

### Как добавить новый язык

1. Скопировать `src/i18n/locales/ru.js` в `src/i18n/locales/<code>.js` и перевести значения.
2. Зарегистрировать язык в `src/i18n/locales/index.js`: добавить импорт словаря в
   `dictionaries` и запись в `localeMeta` (`label`, `short`, `flag`, `intl`, `aliases`).
3. Перезапустить dev-сервер. Переключатель языка, форматирование чисел и дат,
   автоопределение по языку Telegram — подтянутся автоматически.

Больше нигде в коде править ничего не нужно: компоненты обращаются к ключам,
а не к строкам. В dev-режиме словари сверяются между собой и в консоль
выводится список недостающих ключей.

### Определение языка при запуске

1. явный выбор пользователя в приложении (`localStorage: space.lang`);
2. `language_code` из Telegram Web App;
3. колонка `users.lang` из БД бота (приходит в bootstrap и применяется, пока нет явного выбора);
4. язык браузера;
5. русский (`ru`) как язык по умолчанию.

Все запросы к API отправляют заголовок `Accept-Language` с текущей локалью —
на случай серверной локализации ответов в будущем.

### Числительные

Склонения хранятся отдельными ключами с суффиксами `_one/_few/_many/_other`
и выбираются через `tp(key, count)` и `Intl.PluralRules`, поэтому формы
корректны для ru/uk/en (например `1 монета`, `2 монеты`, `5 монет`, `1 coin`, `2 coins`).

## Оформление: цвета и шрифты

И цвета, и шрифты собраны в «один файл» — чтобы менять внешний вид приложения без поисков по стилям.

| Что | Файл | Как переключить |
| --- | --- | --- |
| Цвета (палитры) | `src/theme/colors.js` | пресет `cosmic` в `defaultPalette` или `?theme=cosmic` в адресе |
| Шрифты (типографика) | `src/theme/fonts.js` | пресет `onest`/`system` в `defaultTypography` или `?type=onest`, `?type=system` в адресе |

`src/theme/fonts.js` описывает пресеты (`tech` — Unbounded + Manrope + JetBrains Mono,
`onest`, `system` — полный откат к системным шрифтам без загрузки из сети) и на старте
подключает веб-шрифты одним `<link>` и раскладывает значения в CSS-переменные
`--font-display` / `--font-body` / `--font-mono` (плюс вес и трекинг заголовков).
Вызов — в `src/main.jsx` рядом с `applyThemeColors()`.

Свои файлы шрифтов (офлайн, без внешних CDN): положи `.woff2` в `public/fonts`,
добавь в пресет массив `faces` (`{ family, src, weight, unicodeRange }`) и очисти `url` —
файл сам соберёт `<style>` с `@font-face` (`fontFaceCss()`).

Откат: `?type=system` в адресе мини-аппа (без пересборки) или `defaultTypography = 'system'`
в файле. Все три шрифта основного пресета есть в Google Fonts и поддерживают кириллицу;
если сеть недоступна, браузер откатывается к системному стеку из тех же переменных.

## Админка

Админ-панель открывается из «Профиля» → «Админ-панель» и доступна только владельцу бота
(строка в таблице `owner` либо `OWNER_CHAT_ID` / `ADMIN_BOOTSTRAP_CHAT_ID` в `.env`).

Вход в админку — одним из двух способов, оба задаёт сам владелец:

| Способ | Что вводится | Где лежит хеш |
| --- | --- | --- |
| Фигура | 4–9 разных точек сетки 3×3 | `owner.mini_app_pattern_hash` — `v1:<соль>:<хеш>` |
| Код | ровно 4 или 8 цифр | `owner.mini_app_code_hash` — `v2:<длина>:<соль>:<хеш>` |

Экран входа сам подтягивает настроенные способы (`GET /api/admin/access`) и показывает нужную
вкладку «Фигура» / «Код»; если настроены оба — появляется переключатель. Смена способа — кнопка
«Доступ» в шапке админки: там выбирается способ и длина кода (4 или 8 цифр), значение вводится
дважды для подтверждения, ненужный способ можно удалить (последний удалить нельзя).

Вверху окна «Доступ» есть тумблер защиты:

| Режим | Что происходит |
| --- | --- |
| «С паролем» | вход как обычно: фигура или код (`owner.mini_app_access_off = false`) |
| «Без пароля» | админка открывается сразу, фигура и код не спрашиваются (`owner.mini_app_access_off = true`) |

Пароль — второй фактор, первый остаётся всегда: пускает только владелец бота из `owner`. Поэтому
«вход без пароля» доступен ровно тому же Telegram-аккаунту, что и раньше, просто без фигуры и
кода — на экране входа появляется кнопка «Войти». Хеши при выключении не стираются: вернув
«С паролем», владелец получит прежний способ входа.

| Где | Что делает |
| --- | --- |
| `src/screens/AdminScreen.jsx` | вход по фигуре/коду, счётчик попыток, вкладки админки |
| `src/components/admin/PatternLock.jsx` | фигура как на блокировке телефона: линия ввода, подсветка точек, тряска при ошибке |
| `src/components/admin/CodePad.jsx` | ввод кода: индикаторы набранных цифр и клавиатура 0–9 |
| `src/components/admin/AdminAccessModal.jsx` | окно «Доступ»: тумблер «с паролем / без пароля», выбор способа, длина кода, сохранение и удаление |
| `server/index.js` (`/api/admin/login`, `/api/admin/access`) | запись и проверка хешей, блокировка на минуту после 3 ошибок |

Первый вход: пока в `owner` нет ни фигуры, ни кода, первый ввод владельца (тот, кто указан
в `ADMIN_BOOTSTRAP_CHAT_ID`) становится его способом входа. Колонки `mini_app_pattern_hash`,
`mini_app_code_hash` и `mini_app_access_off` приложение добавляет при старте
(`ensureAdminAccessSchema`); если у пользователя БД нет прав `ALTER`, выполни
`server/admin_setup.sql` от владельца БД:

```sql
ALTER TABLE owner ADD COLUMN IF NOT EXISTS mini_app_code_hash text;
ALTER TABLE owner ADD COLUMN IF NOT EXISTS mini_app_access_off boolean NOT NULL DEFAULT false;
```

`ensureAdminAccessSchema` сначала проверяет колонки по каталогу, а `/api/admin/login`
и `/api/admin/access` перепроверяют его при запросе, поэтому после ручного `ALTER`
владельцем БД всё включается само: права `ALTER` приложению не нужны и перезапуск API
не требуется. Пока нет колонки `mini_app_code_hash`, окно «Доступ» в админке отвечает
ошибкой «Владелец БД должен добавить колонку owner.mini_app_code_hash», а вход по коду
отключён. Так же ведёт себя тумблер «Без пароля» без колонки `mini_app_access_off`:
«Владелец БД должен добавить колонку owner.mini_app_access_off».

### Режим «тех. работы»

В шапке админки есть кнопка «Включить тех. работы» (`FiTool`). Пока режим включён,
`GET /api/bootstrap` отдаёт данные только владельцу бота, а всем остальным — один флаг
`maintenance`, и приложение показывает заглушку «Идут технические работы» с кнопкой
«Проверить снова» (`MaintenanceScreen` в `src/screens/SetupScreens.jsx`). Владелец
работает как обычно и видит админку, поэтому выключить режим можно в любой момент.

| Где | Что делает |
| --- | --- |
| `GET /api/admin/maintenance` | текущий флаг (`requireOwner` + сессия админки) |
| `POST /api/admin/maintenance` | `{ enabled: true \| false }` — включает и выключает режим |
| `server/maintenance.json` | сам флаг: `{ enabled, updatedAt }`, файл в `.gitignore` |

SQL не нужен: настройка одна, поэтому она живёт в JSON-файле рядом с сервером и
переживает перезапуск API. Удали файл — режим выключен.

## Миссии

Экран «Миссии» — ежедневный цикл заданий и вех дня: за забранные задания дают XP,
XP открывает вехи с подарочными кейсами. Цифры продублированы в нескольких местах,
поэтому при изменении правьте их согласованно:

| Где | Что задаёт |
| --- | --- |
| `server/index.js` (`missionMilestones`) | пороги вех и кейсы-награды |
| `server/missionsApi.js` (`missionActionCatalog`, `missionDefaults`) | какие действия умеет сервер и стартовый набор заданий |
| Админка «Задания» (`/api/admin/missions`) | сами задания в БД: тексты, цель, XP, награда, ритм сброса, цели-подписки |
| `src/config/missions.js` | иконка, тон и порядок карточек по коду действия (`bot` / `app`) |
| `src/config/casesMeta.js` (`missionMilestones`) | пороги вех для рельса прогресса |
| `src/i18n/locales/*.js` (`missions.definitions.<id>`) | название и описание задания для игрока |

Задания дня (дают XP и наполняют вехи):

| id | Задание | XP | Проверка на сервере |
| --- | --- | --- | --- |
| `activity_today` | одно сообщение в чате со Space | 100 | `user_activity_daily` (fallback `users.last_activity`) |
| `groups_today` | активность в 2 разных чатах | 100 | `users.groups_activity` |
| `messages_today` | 25 сообщений за день | 180 | `user_activity_daily` |
| `banana_ready` | `!банан` | 140 | `users.banana_cooldown` минус 8 часов |
| `bag_ready` | мешок в меню `!рулетка` | 140 | `users.bag_cooldown` минус 8 часов |
| `roulette_ready` | ставка в `!рулетка` | 140 | `users.roulette_last_activity` |
| `case_open_today` | открыть кейс в Space App | 200 | `case_openings` |

Сумма XP всех заданий дня — 1000, ровно столько же стоит последняя веха.

Вехи дня: 250 XP — Бомж кейс, 500 XP — ещё два Бомж кейса (`quantity: 2`),
750 XP — Стандартный, 1000 XP — Необычный. Кейсы выдаются автоматически в момент
забора задания, перешагнувшего порог.

Рельс прогресса («линия дня», блок `MISSIONS` в `src/styles.css`) — одна
непрерывная линия без стыков и штриховки. Шкала идёт от центра первого кейса до
центра последнего, поэтому крайние кейсы стоят ровно по краям панели, а каждый
кейс — точно под своей засечкой. Заливка растёт от левого края линии к текущему XP
и на пороге совпадает с засечкой; отметки вех: тусклая — впереди, ледяная — порог
закрыт, мятная — кейс забран, белая пульсирующая — ближайшая цель.

Экран миссий сам опрашивает `GET /api/missions` раз в 5 секунд (и сразу после
возврата во вкладку), поэтому задания «оживают» без перезахода. Ручка отдаёт только
`missionProgress`, `missionMilestones` и `missions` — тяжёлый bootstrap не тянется.

Недельные задания (`kind: 'weekly'`) XP не дают — за них сразу кладётся кейс:
«Марафон недели» (250 сообщений → Необычный) и «Дисциплина» (активность 5 дней из 7
→ Стандартный). Неделя начинается в понедельник 00:00 по МСК.

Сброс: задания дня и вехи — в 00:00 по МСК (по `mission_progress.updated_at`),
недельные — по токену с датой понедельника. Прогресс хранится в `mission_progress`
(`xp`, `claimed_milestones`, `claims`), дополнительная схема не нужна.

### Названия и ритм в админке

Список заданий собирается из каталога действий (`missionActionCatalog`), поэтому
подпись есть даже у задания без своих текстов: код действия берётся из словаря
`admin.missions.actions.<code>` («Сообщение в чате», «Сообщения за день»,
«Подписка на каналы»…), а сам код (`activity_today`) показывается рядом моно-чипом.
Свой текст из редактора всегда важнее словарного.

Плашка «Ритм заданий» ставит один интервал сброса сразу всем повторяющимся заданиям
(`missionCadencePresets` в `server/missionsApi.js`, часы у пресетов уникальны,
подписи — в `admin.missions.cadenceNames.<id>`):

| id | Часы | Подпись |
| --- | --- | --- |
| `pulse` | 12 | Дважды в день |
| `orbit` | 24 | Раз в день |
| `helix` | 48 | Раз в 2 дня |
| `drift` | 72 | Раз в 3 дня |
| `selene` | 168 | Раз в неделю |
| `lunar` | 336 | Раз в 2 недели |

Чтобы включить задание, хватит тумблера в админке. Чтобы добавить НОВУЮ проверку:
опишите действие в `missionActionCatalog` (`server/missionsApi.js`), добавьте ветку в
`missionReady` и показатель в `missionProgressMetrics` (`server/index.js`), иконку и
тон — в `src/config/missions.js`, подписи — в `admin.missions.actions.<code>` и
`missions.definitions.<id>` словарей.


## Кейсы

Экран кейсов собран как «лут-терминал» — та же техно-система, что у миссий
(`ops-hero` / `ops-panel` с угловыми скобками и моно-подписями), но в золотой
гамме склада: панели, карточки капсул и журнал открытий выглядят одним набором.

| Блок | Что показывает | Классы |
| --- | --- | --- |
| Шапка-терминал | надзаголовок, название раздела и пояснение | `ops-hero loot-hero`, `ops-hero__eyebrow` |
| Рейка капсул | витрина в две колонки: название, крупный арт, цена в звёздах и счётчик запаса | `loot-rack`, `loot-card` |
| Детальная страница кейса | арт и описание, состав капсулы со шансами, открытие из склада и покупка | `case-detail__art`, `loot-slots`, `case-detail__actions` |
| Подарки Telegram | собранные подарки с моно-кодом и количеством | `loot-gift` |
| Журнал открытий | последние открытия, по 5 на страницу (свайп или стрелки) | `loot-log` |

Плитка рейки — одна большая кнопка (`role="button"`, Enter/Space): описание, состав
и покупка переехали на детальную страницу, поэтому в сетке двух колонок осталось
только то, по чему выбирают кейс, — название, арт, цена и запас. Роутера у
мини-аппа нет, «страницу» листает сам экран: карточка шлёт `caseId` в состояние
`detailCase` (`showCase` / `hideCase` в `src/screens/CasesScreen.jsx`), а «назад»
возвращает рейку.

Состав капсулы детальная собирает из `contents` каталога (`buildCasePrizes` в
`src/utils/casePrizes.js`): средние плитки `loot-slot` (`CasePrizeSlot.jsx`)
показывают знак приза, название, количество и шанс — сводку `odds` с сервера, а без
неё долю веса строки. Подарок Telegram рисуется Lottie-анимацией (`GiftArt.jsx` над
`GiftLottie.jsx` — он же умеет показать картинку из каталога и эмодзи-заглушку), под
названием стоит подпись «подарок Telegram», а сверху висит его цена в звёздах из
каталога юзербота (`data.giftsCatalog`). Файл анимации приходит с того же домена:
`GET /api/gifts/sticker/{id}.json` в `server/giftsApi.js` — открытый прокси к
юзерботу (плеер Lottie не умеет передавать initData), закрытый только на чтение
анимации по id. `giftId` в строке наполнения отвечает только за то, что видно в
слоте и в выпадении: награду всё равно определяет сервер (`createCaseReward` →
`grantGiftReward` выдаёт подарок-«мишку» в коллекцию), поэтому `giftId` едет в ответ
открытия кейса как подсказка для анимации.

Уникальный (коллекционный) подарок — единственное исключение: это не «подарок по
умолчанию» с чужой картинкой, а конкретный экземпляр с аккаунта юзербота, и выдать его
из бота нельзя — подарок вправе передать только владелец. Поэтому выбор такого подарка
в пикере помечает строку наполнения как `giftKind: 'unique'` и запоминает адрес подарка
на аккаунте (`giftSlug` и `giftMsgId`, см. `pickGift` в `CaseContentEditor.jsx`),
сохранение кейса проверяет такой id по списку подарков аккаунта (`assertContentsGifts` в
`server/casesApi.js`), а открытие кейса награду не выдаёт, а **передаёт**: юзербот
(`POST /api/gifts/transfer` → `payments.transferStarGift`) переводит экземпляр игроку, и
награду игрок видит только тогда, когда подарок действительно ушёл с аккаунта. Передача не
удалась — открытие кейса откатывается целиком (кейс остаётся у игрока): молча выдать вместо
уникального подарка «мишку» было бы хуже честной ошибки. Вся выдача подарков собрана в
одном модуле — `server/caseGifts.js` (см. «Выдача подарков и логи» ниже).
Анимация такого подарка — его модель из атрибутов, поэтому у неё своя ручка
(`/api/gifts/sticker/unique-<id>`), а номер экземпляра (`#35 651`) виден и в пикере, и
в строке наполнения, и в выпадении. Подложка — тоже его собственная: цвета и узор из
Telegram (см. ниже, `GiftBackdrop.jsx`).

### Выдача подарков и логи

Подарок из кейса — это настоящий подарок Telegram, поэтому вся выдача собрана в одном
модуле `server/caseGifts.js` (`createCaseGiftDelivery`), а `server/index.js` только
зовёт `deliverGift` и решает, что показать игроку.

| Наполнение кейса | Способ | Что происходит |
| --- | --- | --- |
| уникальный подарок (`giftKind: 'unique'`) | `userbot-transfer` | юзербот переводит экземпляр с аккаунта: `POST /api/gifts/transfer` (`payments.transferStarGift`) |
| обычный подарок каталога (`giftId`) | `bot-sendgift` | бот покупает подарок у Telegram и дарит игроку (`sendGift` Bot API); платит из баланса звёзд, а тот пополняется продажей кейсов |
| строка без подарка, ручной id, `CASE_GIFT_DELIVERY=internal` | `internal` | прежний внутренний подарок-«мишка» в коллекцию профиля |

Обычный подарок нельзя передать с аккаунта, как уникальный: Telegram отвечает
`STARGIFT_NOT_UNIQUE`, поэтому у обычных подарков дорога своя — покупка ботом. Внутренняя
выдача остаётся запасным вариантом для старого наполнения и для отладки: включается
переменной `CASE_GIFT_DELIVERY=internal`, и в логе открытия рядом со способом печатается
причина подмены.

Любой сбой доставки — это `CaseGiftDeliveryError`: транзакция открытия откатывается
(кейс остаётся у игрока, награда не выдаётся), игроку уходит ошибка с **кодом обращения**
(`IS-<время>-<соль>`, `newCaseIncidentCode`) и подсказкой написать в поддержку, а в чат
кейсов (`CASE_RESULTS_CHAT_ID` / `CASE_RESULTS_THREAD_ID`) — лог с тем же кодом: когда,
кто, какой кейс, какой подарок, каким способом и почему не ушёл. Успешное открытие
логируется туда же строкой со способом выдачи. Лог провала отправляется с повтором и
дублируется в журнал сервера: если Telegram недоступен, причина не теряется.

Тексты логов — HTML, обрезаются под лимит сообщения Telegram (3800 символов), время в них
считается по `Asia/Tbilisi` (владелец сверяет лог с сообщениями поддержки). Таймаут покупки
и отправки подарка ботом — `CASE_GIFT_SEND_TIMEOUT_MS` (по умолчанию 20 секунд, меньше
5000 не имеет смысла), передача уникального подарка ждёт юзербот по
`GIFTS_TRANSFER_TIMEOUT_MS` (40 секунд).

`giftId` — **строка цифр**, а не число: у подарков Telegram id девятнадцатизначный
(`6003373314888696871`), а это больше `Number.MAX_SAFE_INTEGER`, и в числе последние
цифры теряются (`…696871` → `…697000`). С потерянным id юзербот подарок не находит и
отвечает 404 — анимация остаётся заглушкой, хотя каталог работает. Поэтому каталог
юзербота разбирается как текст с подписанными кавычками длинными id
(`parseGiftPayload` в `server/giftsApi.js`), а дальше id едет строкой: в каталоге
(`normalizeGift`), в адресе `/api/gifts/sticker/<id>.json` (у уникального подарка ручка
своя — `/api/gifts/sticker/unique-<id>.json`, ключ собирает `giftAnimationKey`), в
`contents` кейса
(`giftIdText` в `server/casesApi.js`) и в ответе об открытии кейса. На клиенте то же
правило держит `giftIdText` в `src/utils/giftCatalog.js`; ручной ввод id в пикере —
текстовое поле, потому что числовое показывало бы id округлённым.

Подарок выбирается в редакторе наполнения
(`GiftPickerPanel` в `CaseContentEditor.jsx`): сверху переключатель источника, ниже
сетка каталога под строкой приза (ровно два подарка в ряд — так карточка остаётся
широкой на телефоне), поиск по названию и id, кнопка обновления каталога
(`GET /api/admin/cases?refresh=1`) и ручной ввод id на случай, когда юзербот
недоступен. Источник меняется одной кнопкой: **«Все подарки»** — каталог Telegram
(`payments.getStarGifts`), **«На аккаунте»** — всё, что лежит на аккаунте юзербота:
полученное, купленное и размещённое на профиле (`payments.getSavedStarGifts`, прокси
`loadSavedGifts` в `server/giftsApi.js`).
Внутри каталога есть вторая пара вкладок: **«Все»** — подарки в свободной продаже,
**«Лимитированные»** — серии с ограниченным выпуском (`limited`, включая распроданные
`sold_out`: такой подарок мог уже лежать на аккаунте). Разложены они на клиенте
(`giftIsLimitedSeries` в `src/utils/giftCatalog.js`), числа рядом с кнопками — размер
каждой вкладки; в режиме аккаунта вкладок нет: там экземпляры, а не серии.
Второй список едет тем же ответом админки (`catalog.savedGifts` и
`catalog.savedStatus`) и схлопнут по подарку: число полученных штук лежит в `count`,
поэтому в режиме аккаунта на карточке видно «×3», а подарки, которые есть на
аккаунте, помечены в каталоге значком с числом. Обычные подарки в этом списке
схлопнуты по id, а уникальные идут отдельными карточками: у каждой свой номер
(значок `#35 651`), своя модель и своя подложка (цвета и узор из Telegram).
«×N» у уникальных не бывает: это разные экземпляры, а не повторы одного подарка.
Список подарков аккаунта юзербот отдаёт вместе с уникальными и размещёнными на
профиле (`exclude_unique=false&exclude_hosted=false`, см. `fetch_saved_gifts` в
`app/user_bot/gifts_logic.py`): Telegram описывает метод как «fetch the full list of
gifts owned, received or hosted by a peer», а hosted-подарки приходят только без
флага `exclude_hosted` — с ним владелец видел на аккаунте один обычный подарок, а
коллекционные, стоящие на профиле, нет. Если юзербот не понимает эти параметры,
сервер повторяет запрос скромнее (`savedGiftRequests` в `server/giftsApi.js`), а
пикер пишет, чего в списке нет (`mode` в `savedStatus`). Подарок, выставленный на
профиль (`hosted`, владелец — кошелёк TON), помечен значком «на профиле»: передать
его с аккаунта нельзя.
Тем же списком юзербот ищет и анимации коллекционных подарков: перед скачиванием файла
`ensure_unique_gift_sticker`/`ensure_unique_gift_pattern` в `app/user_bot/gifts_logic.py`
обновляют реестр подарков аккаунта **вместе с размещёнными на профиле**
(`fetch_saved_gifts(client, exclude_hosted=False)`, см. `_refresh_account_gifts`). С
прежним запросом — по умолчанию `exclude_hosted=true` — подарок, стоящий на профиле, в
реестр не попадал, и на его карточке вместо подарка оставался эмодзи-значок: анимацию
не находили по id экземпляра.
Кнопка «обновить» тянет заново оба
списка. Карточка сетки показывает саму
анимацию подарка: файл качается только для карточек в видимой области и снимается,
когда карточка уезжает (`GiftLottie` с `lazy` — на каталог в полторы сотни подарков
полторы сотни живых плееров не поставить), а пока файл едет, виден знак подарка.
Анимация не единственное, что видно на карточке: под ней лежит **подложка подарка**
(см. ниже), поэтому карточка подарка из каталога выглядит как плитка в каталоге
Telegram, а не как серая рамка.
Промах не приговор: пока карточка в кадре, файл перезапрашивается раз в 30 секунд
(юзербот мог подняться, а владельцу не нужно угадывать, что сетку придётся
прокрутить туда-обратно), а первый промах по подарку пишет в консоль браузера
`[gifts] анимация подарка N не загрузилась (…)` — заглушка выглядит одинаково и при
долгой загрузке, и при ошибке, а причина обычно на стороне юзербота. В логе сервера
это та же строка с причиной: `[gifts] файл подарка недоступен: …` (этой же ручкой
ездит и узор подложки).
Нажатие на карточку подарка не выбирает его сразу, а открывает карточку подарка
(`GiftDetailSheet`): art на подложке подарка, название с номером экземпляра и те же
строки, что в профиле подарка в Telegram — «Коллекция», «Модель», «Узор», «Фон» с
редкостью (значок «3.6%» считается из промилле юзербота), «Владелец», «Наличие»
(«390 094/457 382 выпущено»), «Размещение» (подарок стоит на профиле аккаунта, и
владелец у него кошелёк) и «Ценность». Значок в углу и кнопка «Открыть в
Telegram» ведут на страницу подарка, но она есть только у уникального
(коллекционного) подарка: Telegram отдаёт готовый slug экземпляра
(`https://t.me/nft/<slug>`, `starGiftUnique.slug`). У подарка каталога `slug` не
приходит вовсе, а собранная из названия ссылка в Telegram не открывается (клиент
отвечает `STARGIFT_SLUG_INVALID`) — поэтому кнопки у него нет. Выбор подтверждается
кнопкой в карточке («Выбрать подарок») — она отдаёт
`onPick`. Подарок уже выбранной строки открывается тем же окном по значку ⓘ рядом с
кнопкой смены подарка, но без кнопки выбора — просто посмотреть, что за экземпляр
стоит в призе. Атрибуты с редкостью, владелец, выпуск и оценка приходят из юзербота
(`normalizeGift`/`normalizeUniqueGift` в `server/giftsApi.js`), а строки и подписи
собирает `src/utils/giftCatalog.js`.



#### Подложка подарка

Подарок на карточке — не одна картинка, а слои, как в клиенте Telegram: снизу подложка
самого подарка, поверх неё анимация. Собирает слои `GiftBackdrop.jsx`, он общий у сетки
пикера и у карточки подарка (`GiftDetailSheet`), а цвета и узор приходят готовыми
(`backdrop` в `normalizeGift`/`normalizeUniqueGift` в `server/giftsApi.js`).

У подарка каталога фон — три цвета из `starGift.background`: `center_color` (центр
подложки), `edge_color` (её края) и `text_color` (цвет подписей на ней). У уникального
подарка то же самое приходит из атрибута `starGiftAttributeBackdrop`, и к цветам
добавляется **узор**: Telegram описывает `starGiftAttributePattern` как «a sticker
applied on the backdrop of a collectible gift using a repeating pattern», а
`pattern_color` подложки — как «color of the starGiftAttributePattern applied on the
backdrop». То есть узор — стикер, который красится цветом подложки и кладётся плиткой, и
ровно это делает `GiftBackdrop`: градиент центром наружу (`radial-gradient`) плюс слой с
маской CSS (`mask-image: <узор>`, `background-color: <pattern_color>`).

Файл узора отдаёт юзербот — `GET /api/gifts/sticker/unique/<id>.pattern`
(`handle_unique_sticker_pattern` в `app/user_bot/gifts_api.py`): он скачивает документ
узора того же подарка и кладёт его в кэш рядом с моделью (`<id>.pattern.webp`), а тип
содержимого берёт у документа. Наш сервер проксирует его той же ручкой, что и анимацию
(`GET /api/gifts/sticker/unique-<id>.pattern`, `proxySticker` в `server/giftsApi.js`), и
**не подменяет тип**: по `application/octet-stream` браузер маску не наложит, и подложка
осталась бы одними цветами. Красит узор только картинка, поэтому тип проверяется на
клиенте (`giftPatternUrl` в `src/utils/giftCatalog.js`): если Telegram отдаст узор
анимацией (`.tgs`), маска не соберётся, и карточка просто останется на цветах подложки.

Цвет подписей на карточке тоже из Telegram (`text_color`): у светлых подложек он тёмный,
и белый текст на них не читался бы (тень под текстом держит его читаемым и когда своего
цвета подписей нет). Номер экземпляра уникального подарка лежит лентой в углу карточки —
как в Telegram, а галочка выбора рисуется поверх ленты.

Выключенный юзербот ничего не ломает: каталог приходит пустым, слот подарка
показывает знак приза, а пикер честно пишет «Каталог подарков недоступен» с
причиной (в режиме «На аккаунте» — «Подарки аккаунта недоступны» с той же
причиной) — `ECONNREFUSED` (на `GIFTS_API_URL` никто не слушает), `ENOTFOUND`
(не тот адрес), «таймаут» (юзербот не ответил за `GIFTS_API_TIMEOUT_MS`) или
текст самого юзербота: `юзербот ответил 502: payments.getStarGifts: Telegram
просит подождать 600 сек`. Полный текст с адресом виден и в логе сервера.
Промах кешируется всего на 30 секунд, а успешный каталог — на `GIFTS_CACHE_MS`,
поэтому поднятый юзербот подхватывается сам: ни «обновить» в админке, ни
перезапуск мини-аппа не нужны.

Каталог — это живой запрос в Telegram через юзербот, и он занимает секунды,
поэтому bootstrap его не ждёт: `loadGiftCatalog({ background: true })` отдаёт
приложению текущий снимок, а юзербот опрашивается в фоне (иначе первый экран
висел бы на таймауте). Юзербота ждут только те, кто просит каталог явно: ручка
`/api/gifts` и кнопка «обновить» в админке (`?refresh=1`) — до
`GIFTS_API_TIMEOUT_MS`, по умолчанию 15 секунд. Анимация (`.tgs`) качается из
Telegram при первом показе, поэтому у неё отдельный таймаут
`GIFTS_STICKER_TIMEOUT_MS` (90 секунд), а дальше файл берётся из кэша юзербота.
Передача подарка с аккаунта (`POST /api/gifts/transfer`) — операция из двух шагов в
юзерботе (передать и проверить), поэтому у неё свой таймаут
`GIFTS_TRANSFER_TIMEOUT_MS` (40 секунд): оборвать раньше — риск решить, что подарок не
ушёл, когда он уже ушёл.
Первый показ — это один поход в Telegram, то есть секунды, а не минуты; минутное
ожидание на сетке каталога значит, что файл не приехал, и смотреть надо не в плеер,
а в лог сервера (см. `[gifts] файл подарка недоступен` выше).

Тот же вид плитки повторяет превью в редакторе кейса (`cases-admin-preview` в
`src/components/admin/CaseEditor.jsx`), поэтому админка показывает карточку ровно
такой, какой её увидит игрок.

Данные приходят из bootstrap (`data.cases`, `data.gifts`, `data.caseOpenings`,
`data.giftsCatalog`). Порядок карточек — `caseOrder` в `src/screens/CasesScreen.jsx`;
картинки, цвета и цены — в `src/config/casesMeta.js`, а кейсы владельца — из
`data.caseCatalog` (`buildCaseTypes` в `src/utils/caseCatalog.js`). Стартовые шесть
кейсов из конфига живут без `contents`: их слоты строятся по `odds`.
Сводки склада в шапке нет: запас виден в счётчике на каждой капсуле, а панель
«Доступные кейсы» ограничивается заголовком без счётчика типов.
Тексты — ключи `cases.*`: `heroEyebrow`, `featuredEyebrow`, `available`, `panelTotal`,
`detailEyebrow`, `contents`, `chance`.

Над рейкой стоит блок «Кейс дня» (`featured-case`, компонент
`src/components/cases/FeaturedCase.jsx`): слева название и описание кейса, справа
арт капсулы в кольцах. Заголовка «Сегодня в Space» у блока нет — тексты берутся из
кейса. Какой кейс показывать, задаёт владелец в админке (флаг `featured` у кейса,
ручка `POST /api/admin/cases/featured`), остальное подставляется само.

Фон блока — это «тема» кейса (`mini_app_cases.theme`): `{ mode: 'solid' |
'gradient', from, to, angle }`, где `from`/`to` — токен палитры (`src/theme/colors.js`)
или свой `#rrggbb`. Токен держим токеном, поэтому смена палитры перекрашивает блок
сама; свой цвет остаётся как задан. Фон рисуется так: слева тёмная подложка под
текст, справа яркая заливка фона с артом, поэтому читаемость не зависит от цвета.

Фон правится в редакторе кейса (группа «Фон блока «Кейс дня»», компонент
`src/components/admin/CaseThemePicker.jsx`): библиотека готовых фонов
(`caseBackgrounds` в `src/utils/caseTheme.js` — небула, космос, золото, лёд,
изумруд, орхидея, океан, рассвет, мята, пламя), режим один цвет/градиент, образцы
палитры, свой цвет, наклон градиента и живое превью блока. Любой фон можно
поставить любому кейсу в один тап; по умолчанию каждый кейс получает фон своего
цвета, а пока владелец не трогал цвета — тема следует за акцентом карточки.
Клиентские хелперы — `src/utils/caseTheme.js` (дублируют нормализацию сервера).
Тот же `CaseThemePicker` встроен в панель блока «Кейс дня» (`CaseSpotlightAdmin`):
фон правится прямо там, без похода в редактор кейса, и сохраняется тем же
`PUT /api/admin/cases/:id` (без картинки — её гонять по сети не нужно).

Сам процесс открытия не менялся: награду определяет сервер, а модальное окно
`CaseWheelModal` показывает её выпадение в рейке. Открытие собрано по логике CS2:

| Фаза | Что происходит | Классы и константы |
| --- | --- | --- |
| Разгон | пока сервер выбирает дроп, рейка едет с постоянной скоростью; сдвиг зациклен на период узора, поэтому лента бесконечная, а DOM короткий | `case-reel`, `IDLE_SPEED`, `idleOffset()` |
| Торможение | победный слот считается от текущего положения (`buildLanding`), рейка тормозит по кривой `easeOutSpin` — скорость на входе совпадает с разгоном, на финише слот «доползает» и откатывается на пару пикселей | `LAND_MS`, `LAND_TRAVEL`, `SETTLE_MS` |
| Вспышка | ударный толчок корпуса и цветная вспышка в тон редкости | `case-flash`, `case-modal.is-flash` |
| Выдача | карточка награды с медальоном, лучами, волнами и искрами; закрытие разблокируется колбэком `onReveal` | `case-reveal`, `case-status` |

Всё движение считает один rAF-цикл и пишет `transform` в DOM напрямую — React не
перерисовывается на кадрах. Каждый слот под указателем отбивается тактильным
«тиком» (`HapticFeedback.selectionChanged`).

Громкость выдачи и цвет задаёт редкость награды (`rewardRarities` + `tier` в
`rewardVisuals`, классы `.tier-*` в `styles.css`). Лестница читается без подписей:
**серый** (монеты) → **тил** (астроны) → **ультрафиолет** (предмет) → **орхидея**
(VIP) → **золото** (подарок). Слот рейки красится целиком — рамка, свечение,
полоска сверху, шкала редкости из 1–5 полосок и подпись награды; насыщенность
считает токен `--slot` (0.32…1), поэтому дешёвый дроп уходит в фон, а редкий сразу
цепляет взгляд. Число полосок берётся из порядка ключей `rewardRarities`.

Выдача растёт вместе с уровнем: обычный дроп выдаёт одна волна, с `rare`
добавляются лучи, у `epic` — столб света, вторая волна, широкое кольцо и толчок
`case-hit-hard`, у `legendary` — угольки, ускоренные лучи и золотой блик в
заголовке. Число искр — `sparks` в `rewardRarities`, количество угольков —
`EMBER_COUNT`, порог лучей — `RAY_TIERS` в `CaseWheelModal`. Цвет уровня берётся
из палитры (`src/theme/colors.js`), поэтому тема меняет и выдачу. Тексты:
`cases.landing`, `cases.revealDone`, `cases.rarity.*`.

Если сервер не смог выдать подарок, рейка честно останавливается на ошибке: статус
краснеет (`case-status.is-error`), под текстом ошибки появляется блок поддержки
(`case-status__support`) — код обращения, кнопка «Скопировать» (буфер обмена) и ссылка
«Написать в поддержку». Ссылка общая с блоком помощи документации
(`VITE_SUPPORT_URL`), и без неё кнопка не рисуется — остаётся подсказка. Код обращения
экран берёт из ответа `/api/cases/open` (`code` + `support: true`, собирает
`caseIssueFrom` в `src/screens/CasesScreen.jsx`); у остальных ошибок кода нет. Тексты:
`cases.issueCode`, `cases.issueCopy`, `cases.issueCopied`, `cases.issueSupportText`,
`cases.issueSupportHint`, `cases.issueSupportAction`, а текст самой ошибки —
`errors.server.giftDeliveryFailed`.

Лоток рейки непрозрачный: вместо клетки — спокойные градиенты, два рейла и мягкое
свечение (`case-reel`, `case-reel__bed`), чтобы за крутящимися слотами не
просвечивала сетка терминала и взгляд держался на наградах.

Ширина и зазор слота зашиты в компонент (`ITEM_WIDTH` / `ITEM_GAP`) и продублированы
в CSS — при изменении правь оба места, иначе победный слот встанет мимо указателя.

Файлы `CasesScreenV2.jsx`, `CaseCardV2.jsx` и `CaseWheelModalV2.jsx` ни к одному
экрану не подключены — это прежний черновик, его можно удалять.


## VIP-подписка

VIP продаётся двумя способами, срок у них общий — таблица бота `vip_users`:

| Способ | Как оплачивается | Что включает VIP |
| --- | --- | --- |
| Telegram Stars | `POST /api/vip/purchase-link` → `WebApp.openInvoice` → `POST /api/payments/sync` | заказ `star_vip_orders`, `fulfillVipOrder` |
| Карта и СБП (Tribute) | ссылка подписки из кабинета Tribute → оплата на стороне Tribute | вебхук Tribute → `tribute_events` + `extendVipMembership` |

Тарифы за звёзды живут в коде (`vipPlans` в `server/index.js`), а за реальные
деньги — в кабинете Tribute: приложение показывает цены из
`GET /api/v1/subscriptions`, поэтому сумма на экране всегда совпадает с той,
что Tribute попросит на оплате. Срок берётся из `vipPlans` (`30 / 180 / 365`
дней), так что оба способа дают одинаковые дни и складываются с текущим сроком.

### Что настроить в Tribute

1. Создать подписку в кабинете Tribute с периодами `monthly`, `halfyearly`,
   `yearly` (сроки — как у `vipPlans`: 30 / 180 / 365 дней) и ценами.
   Кабинет не показывает `subscriptionId`, поэтому его не нужно никуда копировать:
   если подписка в кабинете одна, сервер определит id сам по каталогу и напишет
   в лог `[tribute] подписка VIP определена по каталогу: <id>`. Если подписок
   несколько — задать нужную в `TRIBUTE_VIP_SUBSCRIPTION_ID`.
2. Settings (⋯) → API Keys → сгенерировать ключ и указать Webhook URL:
   `https://<домен приложения>/api/tribute/webhook`.
3. В `.env` Mini App положить ключ и ссылку на оплату подписки из кабинета:

```bash
TRIBUTE_API_KEY=...                                   # ключ из кабинета, им же проверяется подпись вебхука
TRIBUTE_VIP_LINK=https://t.me/tribute/app?startapp=s123
# Необязательно: id подписки, если в кабинете их несколько.
# TRIBUTE_VIP_SUBSCRIPTION_ID=1644
# Необязательно: привязка периодов к тарифам (по умолчанию — подбор по сроку).
# TRIBUTE_VIP_PERIODS=monthly:vip_30,halfyearly:vip_180,yearly:vip_365
# TRIBUTE_API_URL=https://tribute.tg/api/v1
```

Пока не заданы ключ и ссылка, `data.tributeVip.enabled` = `false`:
переключатель «Звёзды / Картой» на экране VIP не рисуется, а оплата звёздами
работает как раньше. Тариф для карты показывается только тогда, когда период
есть в подписке Tribute и ему нашёлся тариф в `vipPlans`.

### Как это работает

* `GET /api/v1/subscriptions` кешируется в памяти на 5 минут (ошибка — на
  минуту), bootstrap ждёт его не дольше 1,5 с. Если каталог не ответил, тарифы
  показываются без цены, а сумму человек видит на странице Tribute. Если Tribute
  ответил, но подписки VIP там нет, способ оплаты картой не показывается вообще —
  в лог уходит `subscription-not-found` (`subscription-not-specified`, когда
  подписок несколько, а `TRIBUTE_VIP_SUBSCRIPTION_ID` не задан).
* Вебхук `POST /api/tribute/webhook` проверяет `trbt-signature` — HMAC-SHA256
  тела запроса с API key (сравнение постоянное по времени). Без ключа ручка
  отвечает 503, с неверной подписью — 401. Запрос без подписи (проверка адреса из
  кабинета) и `GET`/`HEAD` на этот же путь отвечают 200 и ничего не меняют —
  иначе Tribute пишет «Не удалось определить адрес вебхука. Проверьте домен» и не
  даёт сохранить Webhook URL. Тестовые и незнакомые события тоже получают 200 и
  VIP не трогают.
* Если подписка VIP ещё не определена (каталог не загрузился или подписка не
  создана), настоящее событие получает 503, чтобы Tribute повторил доставку
  позже и оплата не потерялась.
* События `new_subscription` и `renewed_subscription` продлевают VIP,
  `cancelled_subscription` только пишется в журнал: оплаченный срок не
  отбирается. Чужие `subscription_id` и неизвестные события игнорируются с
  ответом 200, чтобы Tribute не повторял доставку сутки.
* `event_key` (имя события + telegram id + подписка + период + `expires_at`)
  уникален в `tribute_events`, поэтому повтор вебхука не продлевает VIP дважды.
* Тариф для периода подбирается по сроку (`monthly` = 30 дней → `vip_30`,
  `halfyearly` → `vip_180`, `yearly` → `vip_365`), если `TRIBUTE_VIP_PERIODS` не
  задан; заданная карта заменяет авто-подбор. Периоды без тарифа
  (`quarterly`, `trial`) в приложении не продаются, но если человек оплатит их
  на странице Tribute, VIP выдастся по сроку периода (`quarterly` — 90 дней),
  а для периодов без срока (`trial`, `onetime`) — по `expires_at` (не больше года).
* «Проверить оплату» (`POST /api/vip/tribute/sync`) сверяется с
  `GET /api/v1/subscribers` и поднимает срок в `vip_users` до `expireAt`, но
  никогда его не сокращает — дни за звёзды не сгорают. Ручка у Tribute помечена
  как внутренняя, поэтому при её недоступности статус всё равно отдаётся из
  своей базы, а основным источником остаётся вебхук.
* После открытия Tribute экран сам проверяет оплату при возврате
  (`visibilitychange` и `activated` в Telegram), плюс есть кнопка «Проверить
  оплату».

## Документация (Эпик 2)

Раздел «Документация» — это конструктор статей с языковыми версиями и
визуальным редактором: без HTML, только блоки с известной структурой.

### Из чего состоит

| Слой | Файлы |
| --- | --- |
| API и схема БД | `server/docsApi.js` (Express-роутер + `ensureDocsSchema`) |
| Стартовые статьи | `server/docsSeed.js` (режимы `DOCS_SEED`, см. ниже) |
| SQL для ручного развёртывания | `server/admin_setup.sql`, блок «Раздел «Документация»» |
| Конфиг (темы, типы блоков) | `src/config/docs.js` |
| Хелперы редактора | `src/utils/docs.js`, `src/utils/richText.js` |
| Компоненты раздела | `src/components/docs/*` (в т.ч. `DocsHelp.jsx` — блок помощи и частые вопросы) |
| Экран пользователя | `src/screens/DocsScreen.jsx` |
| Раздел в админке | `src/screens/AdminScreen.jsx` → `src/components/docs/DocsAdminPanel.jsx` |

### Данные

* `doc_articles` — статья: `icon`, `theme`, `status` (`draft` / `published`), `sort_order`,
  `topic` (раздел справки: `common` / `home` / `cases` / `shop` / `inventory` / `missions` / `profile`)
  и `is_faq` (показывать в блоке «Частые вопросы»);
* `doc_translations` — языковые версии (`ru`, `uk`, `en`): `title`, `summary`, `blocks` (jsonb).

Таблицы создаются идемпотентно при старте сервера. Если у приложения нет прав
владельца БД — выполни блок документации из `server/admin_setup.sql` и выдай права.

### Стартовые статьи

`server/docsSeed.js` — набор готовых статей (14 обычных + 11 частых вопросов) с
версиями `ru`/`uk`/`en`: как пользоваться приложением, добавление бота в чат,
модерация и фильтры, экономика, кейсы, маркет, VIP, склад, миссии, игры и
RP-команды, профиль и язык интерфейса. Поведение управляется переменной `DOCS_SEED`:

| Значение | Что делает |
| --- | --- |
| не задано / `topup` (по умолчанию) | добавляет отсутствующие стартовые статьи и незаполненные языковые версии |
| `refresh` (алиасы `force`, `update`) | то же плюс перезаписывает существующие версии текущим текстом сида |
| `false` / `0` / `off` | полностью отключает наполнение |

Наполнение выполняется при каждом старте API, поэтому достаточно залить `server/`
и перезапустить процесс — новые статьи появятся сами, дубликаты не создадутся.
Совпадение определяется по заголовку RU-версии: если статью с таким заголовком уже
правили в админке, её текст останется как есть, а недостающие языковые версии
дозаполнятся. Результат видно в логе, например
`Docs schema ready (12 новых статей, 34 языковых версий)`.

Режим `refresh` нужен, когда стартовые статьи в базе уже есть, но их текст устарел
(например, после обновления `docsSeed.js`): выставь `DOCS_SEED=refresh`, перезапусти
API и убери переменную. Статьи, созданные в админке, он не трогает — только те,
чьи RU-заголовки совпадают со стартовым набором.

### API

| Метод | Ручка | Назначение |
| --- | --- | --- |
| GET | `/api/docs?lang=ru` | опубликованные статьи на языке `lang` / `Accept-Language` |
| GET | `/api/docs/:id?lang=ru` | статья с блоками и списком доступных версий |
| GET | `/api/admin/docs` | все статьи со статусами и счётчиками по языкам |
| GET | `/api/admin/docs/:id` | полная статья со всеми языковыми версиями |
| POST | `/api/admin/docs` | создание статьи (`title`, `locale`, `icon`, `theme`, `status`, `topic`, `isFaq`) |
| PUT | `/api/admin/docs/:id` | сохранение метаданных (`topic`, `isFaq` включительно) и языковых версий |
| POST | `/api/admin/docs/:id/move` | порядок вывода (`direction: up` / `down`) |
| DELETE | `/api/admin/docs/:id` | удаление статьи вместе с версиями |

`PUT` синхронизирует версии: язык, которого нет в `translations`, удаляется —
так работает кнопка «удалить версию» в редакторе (пустой список игнорируется).

Если запрошенного языка у статьи нет, сервер отдаёт ближайшую доступную версию
(`ru` → `en` → `uk` → первая доступная) и помечает ответ `isFallback: true`.

### Редактор

* типы блоков: заголовок, текст, список (маркеры / нумерация / чек-лист),
  **плашки** (`badges`), **шаги** (`steps`), **метрики** (`stats`), изображение,
  цитата, врезка, **спойлер** (`spoiler`), **прогресс** (`progress`),
  **кнопка-ссылка** (`link`), код, таблица, разделитель;
  плашки и кнопка-ссылка красятся в акцентные тона (`accent`, `accent-2`,
  `success`, `warn`), прогресс — в тона врезки (`info`, `tip`, `success`, `warn`);
* блоки добавляются кнопкой «+» (в конце статьи или между блоками), двигаются,
  дублируются, удаляются и предпросматриваются так, как их увидит пользователь;
* форматирование текста: `**жирный**`, `*курсив*`, `__подчёркнутый__`,
  `~~зачёркнутый~~`, `` `код` ``, `[ссылка](https://…)`, выравнивание и размер;
* изображения можно вставить ссылкой или файлом — файл уменьшается в браузере
  (до 1400px по длинной стороне) и ужимается в лимит payload;
* оформление: 10 тем (`nebula`, `aurora`, `sunset`, `ocean`, `candy`, `mint`,
  `gold`, `cyber`, `graphite`, `paper`) с градиентами, свечением и звёздами;
* языковые версии создаются и удаляются прямо в редакторе — можно вести,
  например, только RU и EN.

### Куда попадает документация

* **Вкладка «📘 Документация» в нижнем меню** — она заменила вкладку склада,
  поэтому справка всегда в одном касании. Это самостоятельный раздел: кнопки
  «Назад» в его шапке нет, выход — через нижнее меню.
* **Блок «Склад» внизу профиля** — раздел склада переехал туда блоком с иконкой,
  описанием и счётчиком предметов; внутри экрана склада есть кнопка возврата.
* **Кнопка «?» в шапке** (и круглая кнопка в профиле) — открывает документацию
  с фильтром по текущему экрану: кейсы, маркет, склад, миссии, главная, профиль.
  Раздел статьи задаётся в редакторе полем «Раздел справки» (`topic`).
* **Приветственный блок «Новое: Документация»** на главной — показывается один раз,
  закрывается крестиком (флаг в `localStorage`).

Внизу профиля больше нет панели «Активность в группах»: она скрыта, но код и
компонент на месте. Включается одним флагом в `src/config/features.js`
(там же переключатели `docsEntry` и `storeEntry`).

Плитки вверху профиля и на главной показывают сообщения, **кейсы к открытию**
и предметы на складе. Счётчик кейсов (`totalCaseBalance` из
`src/utils/caseText.js`) заменил непонятную плитку «группы»: теперь обе цифры
рядом с сообщениями отражают понятные показатели аккаунта.

### Блок помощи и частые вопросы

Сверху экрана документации всегда виден блок помощи:

* **частые вопросы** — это обычные статьи с флагом `is_faq`: вопрос раскрывается
  прямо в списке (ответ подгружается по требованию и переводится вместе с языком),
  кнопка «Открыть статью целиком» ведёт в полную читалку с темой оформления;
* **строка поддержки** — кнопка ведёт на `VITE_SUPPORT_URL` из `.env`
  (например `https://t.me/your_support`). Если переменная пустая, кнопки нет,
  показывается текст-подсказка «поддержка отвечает в личных сообщениях бота»;
* **чипы разделов** показываются только для тех разделов, где есть статьи,
  и фильтруют список; во время поиска фильтр сбрасывается, чтобы ничего не терять.

Значения `topic` и `is_faq` задаются в редакторе статьи, а в списке админки
видны чипами «раздел» и «частый вопрос».

### Пользовательская часть

Список и статья запрашиваются на текущем языке Web App; чипы языков в читалке
меняют язык приложения (и содержимое статьи, и ответы FAQ) одним касанием.
В карточках статей видны языковые версии, раздел и пометка о фолбэке перевода.

### Валидация

Сервер нормализует блоки: неизвестные типы отбрасываются, строки обрезаются по
лимитам, размер статьи ограничен 4 МБ, картинка — 2 МБ. Все правила собраны в
`server/docsApi.js`.
