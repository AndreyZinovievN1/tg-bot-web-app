# Массовые кейсы: внешняя выдача

Миграции в репозитории подготовлены для ручного применения, но не выполняются при старте API:

1. `case_batch_openings.sql` — журнал запросов ×2–×5 (если ещё не применён).
2. `case_gift_deliveries.sql` — журнал каждой внешней выдачи и ссылка на её запись истории.

Применять сначала на отдельной тестовой PostgreSQL. Роль API должна иметь SELECT, INSERT, UPDATE на новой таблице. Не удалять журналы и не очищать их при обновлениях. Существующие данные и распределение вероятностей миграция не меняет.

## Граница транзакции

Существующий обработчик независимо выбирает каждый приз. Одна транзакция списывает запас кейсов, начисляет внутренние награды существующими функциями, сохраняет все выигрыши, фиксирует внешние обязательства и результат идемпотентного запроса. До COMMIT внешних отправок нет. Повтор requestId не списывает запас и не разыгрывает награды заново.

Отдельный обработчик в процессе Express раз в 5 секунд получает одну готовую выдачу. PostgreSQL advisory lock сериализует обработчики разных экземпляров API. Состояние `sending` и идентификатор попытки фиксируются отдельным COMMIT до вызова Telegram/юзербота. Только затем вызывается существующая отправка. Успешный результат фиксируется вместе с обновлением статуса в истории.

Обработчик не начисляет внутренние награды и не списывает кейсы. Цена оплачивается существующим счётом Telegram Stars при покупке; открытие не оплачивает кейсы повторно.

## Состояния и восстановление

- `queued`: отправка ещё не начиналась либо Telegram явно отклонил её из-за ограничения частоты. Продолжается автоматически, в том числе после перезапуска. До 5 автоматических попыток при подтверждённом 429 с задержкой.
- `sending`: вызов может выполняться. Повторная отправка запрещена.
- `sent`: Telegram/юзербот подтвердил отправку, либо владелец подтвердил её с доказательством. Повторов нет.
- `failed`: отправка точно не началась или явно отклонена, либо уникальный экземпляр уже зарезервирован/выдан другой операцией. Требуется устранение причины владельцем.
- `review`: исход неизвестен. Тайм-аут, обрыв связи и HTTP 5xx не доказывают отсутствие подарка у получателя. Автоматический повтор запрещён. Незавершённый `sending` старше 10 минут также переходит сюда.

После ошибки записи БД уже отправленный подарок не отправляется заново: операция остаётся `sending`, затем `review`. Если другие награды партии уже начислены/отправлены, они сохраняются. Невыданный подарок остаётся обязательством со своим кодом; автоматического возврата кейсов, повторного розыгрыша или замены награды нет.

Публичная лента исключает неподтверждённые внешние выдачи. Собственная история сохраняет факт выигрыша. Экран результатов показывает состояние каждой выдачи и обновляет его отдельным GET, не перезапуская рулетку. Демо не создаёт таких операций и не запрашивает их статусы.

## Проверка владельцем

Используются существующие Telegram-авторизация, административная сессия и проверка владельца. Заголовки такие же, как у остальных admin API: `Authorization: tma …` и `x-admin-token`.

- `GET /api/admin/cases/deliveries` — до 100 неподтверждённых операций, включая получателя, сохранённый подарок, причину и аудит.
- `POST /api/admin/cases/deliveries/:id/resolve` с JSON `{ "action": "retry", "note": "Причина устранена: …" }` — допустим только для `failed`. Возвращает в ту же очередь, без списания/повторного розыгрыша.
- Тот же POST с `{ "action": "confirm_sent", "note": "Проверено по подтверждению провайдера: …" }` — только для `review` или `failed`, после проверки реального получения подарка. Фиксирует результат, не отправляет подарок. Сохраняет владельца, время и пояснение в аудите.

`retry` для `review`, `sending` и `sent` возвращает 409. Не обходить это ограничение SQL-правкой. При `review` отсутствие ответа или отсутствие подарка в кэше не является доказательством неотправки. Если подтверждения у провайдера нет, операция остаётся на проверке. API не предоставляет опасного автоматического «отправить ещё раз».

Статус своей партии: `GET /api/cases/batches/:requestId/deliveries`. Он привязан к авторизованному пользователю; возвращает только код выдачи и состояние, без Telegram ID и адресов подарков.

## Ограничения

Bot API `sendGift` не принимает ключ идемпотентности и возвращает только подтверждение успеха: https://core.telegram.org/bots/api#sendgift. Существующий API передачи юзербота также не предоставляет журнал по ключу запроса. Поэтому полностью автоматическое восстановление неоднозначного внешнего результата с гарантией отсутствия дублей невозможно. Здесь выбран безопасный вариант: сохранять неопределённость и требовать проверки, а не повторять отправку.

Один уникальный физический экземпляр невозможно выдать двум победителям. Вероятности не меняются и приз не подменяется: повторная претензия на такой экземпляр сохраняется как `failed / unique_asset_reserved` для ручного урегулирования.

Путь ×1 не переводился на очередь: его существующая выдача оставлена без изменения. Нельзя считать этот журнал защитой старого пути ×1 или сторонних ручных отправок.

Перед рабочим запуском проверить на тестовой БД и тестовых аккаунтах: миграцию и права, конкурентные запросы/процессы, остановку процесса до/после внешнего вызова, недоступность БД после подтверждения, 429, недостаток Stars у бота, уникальные подарки и ручное подтверждение. Юнит-тесты не заменяют эти проверки.
